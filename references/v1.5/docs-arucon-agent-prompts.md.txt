# 아루콘 — 단계별 에이전트 작업 지시문

버전: v1.5 · 개정일: 2026-09-17  
기준 문서: `arucon-SRS.md` v1.5  
S→D1~D6→Q 구조를 유지한다. v1.5는 D4/D4b의 v3 시각 방향과 D5c의 위젯 역할을 보완하고, 플랫폼 확장 X0~X3를 별도 배정 단계로 추가한다. 문서 반영을 네이티브 앱·모든 확장의 구현 승인/완료로 확대하지 않는다.

> **이 문서는 제품 결정 승인서가 아니다.** SRS의 보완 제안은 해당 DEC가 승인되기 전 운영 동작으로 구현하지 않는다. 원문의 ‘TODO로 남기고 진행’은 ‘결정 대기 보고 + 독립 범위 진행’으로 바꿨다. 수면 방식을 임의로 Health API로 확정하는 지시는 제거했다. D1은 MVP 엔티티만 생성한다.

## 사용 규칙 — 사람과 에이전트 공통

저장소 루트에 `AGENTS.md`, `arucon-SRS.md`, `decisions.md`, `acceptance-tests.md`, 이 파일을 둔다. 저장소 접근이 없는 세션에는 같은 버전의 문서를 첨부한다. 코드 검토·수정 세션에는 관련 코드와 실행 환경도 제공한다. 에이전트가 이전 대화를 기억한다고 전제하지 않는다.

한 세션에 한 단계 또는 한 하위 단계만 배정한다. 제품 정책을 선택해야 하는 작업과 코딩 작업을 구분한다. 각 개발 단계 후 Q를 수행하고, 결함 수정 후 해당 테스트와 핵심 회귀 테스트를 다시 실행한다. 다음 단계의 기능이 없다는 이유로 현재 단계를 실패 처리하지 않지만, 미정 기능을 최종 MVP 완료에서 빠뜨리지 않는다.

**커밋 기본 담당은 사람이다.** 에이전트는 변경·검증 결과를 보고한다. 세션별 명시적 허용이 있을 때만 에이전트가 커밋한다. 머지·출시 승인은 사람이 한다. 원문의 상충하는 커밋 지시를 이 규칙으로 통일했다.

원칙적으로 순서대로 진행한다. D2c나 D5a가 제품 결정으로 막혀도 독립적인 다른 단계는 진행할 수 있다. 단, 미정 기능이 필요한 경로를 mock으로 연결해 실제 완료처럼 보이게 만들지 않는다. D6a는 ‘검증만’ 하는 단계가 아니라 **동기화 서비스 구현 책임이 있는 단계**다. 설계·스키마·outbox는 S/D1에서 먼저 준비한다.

```text

이번 작업: S — 아키텍처·스키마·인터페이스 설계. 기능 코드는 작성하지 마라.

1. 원문 권장 스택을 출발점으로 클라이언트, 로컬 저장, 인증/서버, 네이티브 연동,

4. 먹이/코인 지급, 먹이 섭취, 청소·약, 수면 회복, 아이템 구매의 트랜잭션 경계를 정의해라.

5. outbox, 서버 actionId 중복 방지, 단일 활성 기기/복구 정책의 승인 여부를 반영하고
   서버 요청/응답·오류·검증·허용 전송 필드를 정의해라.
6. config에 원문 시작값과 승인된 추가값을 구분해 매핑해라.
   미정 산식·상품·분기값을 숫자 0이나 유효한 기본값으로 채우지 마라.
7. 엔진 함수·어댑터 시그니처, 대표 입력/출력과 실패 상태를 작성해라.

   함수 이름은 제안 가능하지만 도메인 규칙을 UI에 옮기지 마라.
8. 원본 데이터가 서버·로그·분석으로 빠져나갈 수 있는 경로와 네이티브 기능 제한을 검토해라.
```

# D. 개발 단계

## D1. 프로젝트 뼈대 + config + MVP 저장 기반

```text

이번 작업: D1 — 승인된 S 설계에 따른 최소 실행 기반.

범위 밖: 펫 화면, 완성된 게임 규칙, 네이티브 헬스 읽기, 실제 결제.

완료 조건: 저장 제약·마이그레이션 실패 보존·미정 config 차단 테스트 실제 통과.
```

# Q. QA 단계 — 별도 세션 권장

코드·동일 버전 문서·현재 검증 단계·승인 기록·실행 환경을 제공한다. 이전 에이전트의 설명만으로 판단하지 않는다. 별도 세션은 보완 검토 방식이며 테스트의 대체물이 아니다.

```text
너는 아루콘 프로젝트의 QA 담당이다. 이번에는 코드를 수정하지 마라.
AGENTS.md, arucon-SRS.md, decisions.md, acceptance-tests.md와 검토 대상 코드를 읽어라.
검증 범위는 사용자가 지정한 현재 단계다. 최종 QA라면 SRS 14장 전체다.

1. 적용 FR/승인 DEC/AT ID를 먼저 매핑해라. 코드·실행 근거 없이 통과시키지 마라.
2. 가능하면 실제 테스트·타입검사·린트·빌드를 실행하고 명령/환경/결과를 남겨라.
   실행이 불가능하면 이유와 필요한 환경을 적고 확인 불가로 표시해라.
3. 다음 핵심 위반 경로를 우선 검색하고 실제 호출 경로로 확인해라.
   - 걸음·수면·위젯→EXP 직접 지급 / 부재 중 식사조건 없는 EXP 지급
   - 자동급식 효율 차별·식탁 재고 이동 의무·몰래 구매·화장실 유지비
   - 무료 터치 자원 손실 / 성격·건강 기록으로 능력 서열화
   - 실제 걷기/달리기→펫 체력 감소
   - 청결 외 원인으로 기운 없음 발생 / 약 없는 회복 불가
   - 낮은 체력으로 깨어 있는 펫의 먹이 섭취 차단
   - 상한으로 기존 먹이 차감 / 중복 정산 / 부분 저장
   - 효율 현금 구매 또는 현금→코인 우회
   - 원본 데이터 서버·로그·분석·크래시 전송
   - P2/P3 선행 구현 / config 밖 밸런스 수치 / 미승인 DEC의 실제 적용
   - 비난 문구·사망·영구 손실
4. 시간·수면0/무기록·동면·앱 종료/재시도·복구 경계값을 AT 문서와 대조해라.
5. 테스트 기대값이 SRS와 다르면 코드를 편들거나 테스트를 완화하지 말고 충돌을 보고해라.
6. 다음 상태를 구분해라:
   충족 / 미충족 / 결정 대기 / 해당 단계 범위 밖 / 확인 불가.
   앞으로 만들 기능이 현재 범위 밖이라는 이유로 현재 단계 전체를 실패시키지 마라.
   반대로 최종 MVP QA에서는 범위 밖 처리로 MVP 요구사항을 누락하지 마라.

보고서:
- 범위·문서 버전·코드 버전·실행 환경
- 치명적 원칙 위반 / 요건 미충족 / 경미한 문제
- 각 문제의 FR·AT ID·파일/위치·재현 절차·기대/실제·영향
- 실제 실행 명령/결과와 확인 불가 항목
- 단계별 수용 기준 표. 최종 QA면 SRS 14장 전체 표
- 수정 후 다시 실행해야 할 테스트
```
