# 영향 기반 검증 정책

v1.7 · ENG-01 유지 · 기본 원칙: **관련 검사 + 저장소 필수 검사 + 변경에 맞는 증거**

## 1. 범위 선택

파일 개수 대신 동작·데이터·권한·표현의 영향을 판단한다. 아래 여러 행에 걸치면 합집합을 적용한다. 새 위험이 없고 선택한 검사와 필수 검사가 충족되면 무관한 전체 테스트를 추가하지 않는다. 의존성·빌드 설정·공유 엔진을 바꾼 작업은 단순 UI 수정으로 분류하지 않는다.

| 변경 | 최소 검증 | 확대 조건 |
|---|---|---|
| 문서 오타/설명 | 문서 구조·링크, 관련 FR/DEC/AT 정합성 | 실행 명령/설정도 바꾸면 파싱·계약 검사 |
| AGENTS/스킬/역할 설정 | TOML/YAML·경로·보호 경계·발동 시나리오 설계 | 실제 호스트 도입 시 역할/모델/권한/스킬 인식 검사 |
| 버튼/패널/방 배치 | 해당 조작·작은 화면 잘림·터치 영역·변경 전후 캡처 | 입력/도메인 연결이 바뀌면 자원 중립·중복 검사 |
| 표정/보행/탄성 | 상태 전환·두 성격·동작 줄이기·전후 영상 | 공통 actor나 여러 상태 영향이면 모션 회귀 전체 |
| 활동/급식/EXP/시간/동면 | 관련 도메인·경계·중복·급식 동등성 검사 | 공통 엔진/정산에 영향이면 도메인 전체 |
| 저장/동기화/권한/건강정보 | 실패/복구/트랜잭션/허용 필드·관련 통합 | 실제 OS/서버 연동 범위이면 승인된 환경에서 검증 |
| 빌드/의존성/렌더러 | 영향 런타임의 빌드·호환성·주요 흐름 | 공유 설정이면 지원 대상 매트릭스로 확대 |
| Figma 쓰기 | 계정/대상/범위, 편집 ID, 재조회·실제 렌더 | 이미지/전환/컴포넌트 변경 시 해당 부분까지 검증 |
| 출시 후보 | 승인된 출시 범위 전체 필수 검사·실기기·운영 게이트 | SRS 14장의 누락 없는 판정 |

검사할 수 없으면 “확인 불가”다. 환경 부족은 면제가 아니고, 다른 독립 작업을 진행할 수 있다는 뜻이다. 제품 결정 대기와 테스트 실행 불가를 혼동하지 않는다.

## 2. 명령의 기준

[commands.json](../validation/commands.json)은 **명령 목록**이지 성공 기록이나 자동 실행 스크립트가 아니다. `cwd_kind`, 전제 파일, 필요한 실행 환경, 생성하는 산출물을 먼저 확인한다. 실제 저장소에 더 강한 필수 검사가 있다면 합쳐 실행한다. 없는 `make test`/`npm test`를 가정하지 않는다.

문서 묶음 자체 검사(이 묶음 루트):

```sh
python -m pip install -r validation/requirements.txt
python validation/check_workflow.py
```

설치 명령은 사용자가 선택한 개발 환경에서 최초 준비할 때만 필요하다. 이미 PyYAML이 있으면 설치하지 않는다. 의존성 설치가 금지된 환경에서는 이를 실행하지 않고 전제를 보고한다. 정적 검사기는 외부 서비스에 접속하거나 제품 테스트를 실행하지 않는다.

기존 v3 프로토타입 소스가 따로 있을 때, **그 폴더 안에서** 사용하는 확인된 명령:

```sh
node --test tests/engine.test.cjs
node --test tests/motion.test.cjs
python build.py
```

Node 명령은 파일 존재와 import 경로를 확인했다. 이번 문서 개정에서 다시 실행하지 않았으며, 통과 기록으로 기재하지 않는다. build.py는 번들 HTML을 쓰므로 소스만 읽는 검토자가 실행하지 않는다.

`python tests/browser_test.py`와 `python tests/render_video.py`는 현재 v3 소스에 있지만 `/usr/bin/chromium` 경로 및 환경별 실행 옵션에 의존한다. macOS/Windows의 그대로 실행을 보장하지 않는다. Playwright·브라우저·영상용 ffmpeg·출력 폴더가 필요하며, 환경에 맞는 별도 이식 작업을 한 뒤 실행한다. 임의로 `--no-sandbox`를 일반 사용자 환경 기본 설정으로 권하지 않는다. 기존 테스트의 HTML 주입·메모리 저장 fixture는 실제 Safari·저장 지속성·프레임 성능 검증이 아니다.

## 3. 시각 검증 증거

레이아웃 변경에는 viewport·배율·코드 revision/작업 상태를 기록한 전후 캡처를 남긴다. 모션 변경에는 idle→시선/회전→이동/정지, 접촉 전→눌림→복원, 두 성격 비교의 관련 구간을 남긴다. 모든 작업에 모든 동작 영상을 새로 만들 필요는 없다.

핵심 확인: 바닥 접촉·귀의 지연·과도한 상시 흔들림 없음, 작은 크기에서도 읽히는 시크 눈매·입, UI가 가리지 않는 이동 영역. 이상은 시각 검토 결과로 기록한다. 설정한 인코딩 fps와 실기기 측정 fps를 구분한다.

생성형 이미지/영상은 디자인 시안일 뿐 실행 증거가 아니다. 기존 영상·정지 화면은 해당 revision의 참고이며 수정된 코드의 새로운 실행을 입증하지 않는다.

## 4. 스킬 발동 검증

[skill-trigger-cases.json](../validation/skill-trigger-cases.json)에 양성·음성·경계 사례 18개를 둔다. 같은 프롬프트를 실제 배정 모델별로 반복 평가하고 호출 여부와 결과를 기록한다. 키워드만 겹치는 무관한 요청에서 오발동하지 않는지도 본다. 각 사례 3회는 초기 실험안이며 승인된 비용 범위 안에서 실행한다.

**현재 18개 모두 NOT_RUN**이다. 정적 파일 파싱이 통과해도 모델의 실제 스킬 선택률이 검증된 것은 아니다. Figma 사례는 합성 도구 또는 읽기/계획 전용 dry-run으로 평가한다. 발동률을 측정하기 위해 실제 파일을 반복 생성·편집하지 않는다.

## 5. 검증 담당과 실패

read-only 검토자는 제품 코드·설정·결과물을 바꾸지 않는다. 캡처/캐시/로그 생성이 필요하면 총괄이 허용한 일회용 환경에서 실행하고 산출물만 전달한다. 실행자가 자기 코드 수정과 증거를 맡은 경우에도 별도 검토자는 원문·증거와 대조한다.

실패 시 이번 변경의 원인인지 확인한다. 범위 안 실패는 수정 후 해당 검사를 재실행한다. 범위 밖은 재현과 영향을 보고한다. 테스트를 삭제하거나 기대값을 낮춰 성공으로 만들지 않는다. 정당한 기대값 변경은 제품 승인·명세·코드를 함께 추적한다.

## 6. 완료 상태

`충족 / 미충족 / 결정 대기 / 해당 단계 범위 밖 / 확인 불가`는 요구사항 판정이다. 실행 상태 `미실행 / 실행 성공 / 실행 실패`와 구분한다. 기술 테스트 통과, 시각 검토, 사용자 승인, 원격 저장 완료를 한 단어 “완료”로 합치지 않는다.
