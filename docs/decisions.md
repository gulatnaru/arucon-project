**DEC-19~23의 서술된 제품 방향 5건은 사용자 요청으로 승인 반영했다.** 아래 DEC-01~18은 v1.3 이력이며 부분 대체를 표시한 항목 외에는 이전 미승인 상태를 유지한다. 가격·산식·기간·실서비스 승인으로 확대하지 않는다.

## 1. 사용법

제품 규칙의 상세 내용은 SRS에 둔다. 이 파일에는 그 규칙을 왜 보완하는지, 어떤 선택이 남았는지, 누가 무엇을 승인했는지를 남긴다. 승인 시 SRS·테스트·config를 같은 변경 묶음에서 갱신한다. 이 파일의 문구만 바꾸고 SRS를 방치하지 않는다.

| 상태 | 의미 |
|---|---|
| OPEN | 산식·정책·필수 값이 아직 충분히 정의되지 않음 |
| PROPOSED | 실행 가능한 구체적 안을 제안했지만 승인 전 |
| APPROVED | 사람이 선택안·값·범위를 승인했고 SRS에 반영됨 |
| APPROVED_DIRECTION | 명시된 제품 방향만 승인. 미정 수치·기술·출시 세부는 포함하지 않음 |
| REJECTED | 제안 거절. 대안 승인 전에는 기존 공백이 해소되지 않음 |
| SUPERSEDED | 새 결정으로 대체됨. 과거 이벤트 재현용 이력은 유지 |
| PROTOTYPE_ONLY | 합성 데모 전용. 운영 승인이나 실제 건강/결제 데이터로 전용 금지 |

승인 전 제품 동작을 운영에 연결하지 않는다. 합성 데이터 fixture, 인터페이스, 지원 환경 조사, 확정 범위 개발은 가능하다. **OPEN 항목이 존재한다는 이유만으로 독립적인 모든 작업을 멈추지는 않는다.** 반대로 TODO를 달았다는 이유로 미정 기능을 완성했다고 보고하지 않는다.

## 2. 검토 순서

이번 파일형 PROTO는 DEC-26의 합성 검증 범위다. 운영 개발에서는 먼저 DEC-12의 기술 선택과 DEC-02·03·25의 정산 계약을 검토한다. 다음으로 DEC-04·06·07·15의 펫 상태 기본안을 검토하면 핵심 루프 프로토타입을 진행할 수 있다. 실제 수면·개별 분기·상점·가입·출시 연결은 DEC-05·08·09·11 등 관련 OPEN 결정이 추가로 필요하다.

사용자에게 승인 요청을 정리할 때는 **수면, 돌봄/동면, 외형, 상점, 계정/데이터, 기술/운영**의 주제별로 묶는다. 18개 번호를 의미 설명 없이 한꺼번에 선택하게 하지 않는다. 묶음 승인이라도 승인된 ID와 선택안은 기록한다.

## 3. 결정별 기록

### DEC-01 — 권한·페도미터·백그라운드의 지원 범위

**상태: PROPOSED** · SRS 4-2, 4-4, FR-2, FR-NF.2 · 영향: D3

원문은 권한 거부 시에도 집계 성공을 요구한다. 보완안은 ‘별도 권한·기기 기능이 허용하는 대체 경로’와 ‘측정 불가 안내’를 모두 정상 처리로 정의한다. HealthKit의 빈 읽기 결과를 읽기 거부로 단정하지 않는다. 백그라운드는 지원 환경에서 수집·재조회하고 접근할 수 없는 기록은 복원 가능하다고 약속하지 않는다.

승인할 것: 이 조건부 지원 범위를 채택할지. 지원 OS·센서·기기와 실기기 검증 표는 DEC-12에서 확정한다. 기준은 SRS 부록 EXT-01~03의 플랫폼 사실이지 성능 실험 결과가 아니다.

승인할 것: (1) 시간대 고정, (2) 당일 공급자 잠금, (3) 상한 초과분 미지급, (4) 분수 이월, (5) 과거 수정·지연 입력 처리, (6) 활동 연결 전 기록 제외. 각각 다른 안을 택하면 SRS와 예시를 함께 수정한다.

절충: 단일 소스 잠금은 중복 방지를 단순화하지만 당일 소스 전환을 제한한다. 최고 처리값 방식은 하향 수정 뒤 신규 지급이 잠시 줄 수 있다. 데이터 조회 가능 기간은 DEC-17이 필요하다.

| `piko` | **피코** | 쫑긋형 | 위로 솟은 두 귀가 만드는 뾰족하고 선명한 실루엣 |
| `mongle` | **몽글** | 몽실형 | 둥근 귀, 말린 꼬리, 구름처럼 둥글게 이어지는 실루엣 |

표시 규칙:
- 사용자 개체명(`givenName + "콘"`)은 진화해도 바꾸지 않는다. 예: **구름콘 · 말루**.
- `아루콘`은 초기 공통형 표시명이며, 진화한 개체를 UI에서 다시 “아루콘” 한 이름으로 덮어쓰지 않는다. 내부 계보 식별자 `speciesFamily=arucon`은 유지할 수 있다.
- 형태명은 성격명이 아니다. 말루/모노/피코/몽글 어느 형태에도 향후 승인된 어떤 성격 프로필이든 적용될 수 있다. 특히 기존 “시크형”이라는 가칭을 `모노`로 바꿔 외형과 츤데레/조용함 같은 행동 성격의 혼동을 줄인다.
- 최초 명명 승인은 분기 승인이 아니었다. 이후 v1.9에서 1차 케어 결정표·레벨/config는 DEC-08/24와 함께 승인됐다. 2차 형태명과 최종 아트/리깅 납품 승인은 포함하지 않는다.
- 공개 상표·캐릭터명 법적 클리어런스는 DEC-18 범위다. 이번 결정은 제품 개발용 명명 승인이지 상표 조사 완료가 아니다.

검증: AT-APPEARANCE-04~07. 상세 표시/코드 키는 `character-naming.md`를 따른다.

### ENG-02 — Astra 자율 연속 개발 운영

**상태: APPROVED (개발 운영 범위)** · 승인자: 사용자 · 기록일: 2026-09-18 · 제품 규칙 변경 없음

사용자는 APP-01 이후 매 단계 결과를 사람이 다시 검토한 뒤 다음 단계로 넘기는 방식 대신, **Codex에서 GPT-6 Astra가 허용된 개발 범위를 연속 수행하고 자체 품질 게이트를 통과하면 자동으로 다음 단계로 진행**하는 방식을 승인했다.

운영 규칙:

1. `tasks/AUTO-00-orchestrate.md`가 자율 실행의 최상위 작업이다. APP-01~06은 의존성 순서대로 진행하되, 독립 작업은 병렬 탐색/검토할 수 있다.
2. 각 게이트는 **구현 → 관련 테스트/빌드/시각 증거 → `arucon_reviewer` 독립 검토 → 발견 수정 → 재검증**을 한 묶음으로 본다. 사람이 중간 결과를 확인하지 않았다는 이유만으로 멈추지 않는다.
3. 같은 실패를 고치기 위해 테스트를 삭제·완화하거나 SRS/DEC를 임의 변경하지 않는다. 동일 근본 원인으로 3회 수정 루프 뒤에도 해결되지 않으면 해당 가지를 `BLOCKED`로 격리한다. 독립 가지는 계속 진행한다.
4. **루틴 기술 선택**(파일 구조, 함수명, 테스트 도구, 프로젝트 로컬 의존성, 되돌릴 수 있는 내부 구현)은 Astra가 증거를 남기고 임시 ADR로 결정할 수 있다. 이것은 제품 DEC 승인이나 출시 스택 승인으로 승격되지 않는다.
5. OPEN/PROPOSED 제품 항목은 인터페이스·feature flag·dev fixture·실패 상태까지만 구현한다. 실제 사용자 동작을 요구하는 시점까지 계속 미정이면 해당 기능만 Hard Stop/결정 대기로 남긴다.
6. 실제 건강정보 읽기/처리, 실제 사용자 인증·외부 계정/클라우드 프로젝트 생성, 실결제/스토어 상품, 공개/운영 배포, 원격 push/merge, 공유 권한 변경, 되돌리기 어려운 삭제/파괴적 마이그레이션, 승인 아트의 큰 재디자인은 **Hard Stop**이다. 사용자의 새 명시 승인 없이는 수행하지 않는다.
7. 로컬 소스 수정, 프로젝트 로컬 패키지 설치·lockfile 갱신, 합성 데이터, 로컬 DB, 테스트·lint·typecheck·빌드·에뮬레이터/시뮬레이터 실행은 허용 범위다. 관리자 권한/시스템 전역 설치가 필요하면 우회하지 않고 해당 환경 제약을 기록한다.
8. 실제 기기/OS가 없어 검증 못 하는 항목은 `확인 불가`로 남기되 다른 플랫폼·순수 로직·UI 통합을 계속 진행한다. 웹 프로토타입 증거를 네이티브 앱 실기기 증거로 바꾸어 쓰지 않는다.
9. 자율 실행 중 사용자에게 진행 보고만 하기 위해 멈추지 않는다. **Hard Stop 또는 모든 가능한 게이트 종료**에서만 사람의 결정을 요청한다. 최종 보고에는 PASS/PARTIAL/BLOCKED를 분리한다.
10. 이 운영 승인으로 DEC-01~32의 제품 승인 상태는 바뀌지 않는다. 특히 DEC-05 수면 산식, DEC-08 외형 분기, DEC-09 상품/가격, DEC-11 법정 동의, DEC-12/31 출시 기술·지원 범위와 DEC-24 밸런스는 자동 승인하지 않는다.

상세 중단 조건은 `docs/hard-stops.md`, 실행 루프는 `docs/autonomous-development.md`를 따른다.


### ENG-03 — 멀티모델 자율 라우팅

**상태: APPROVED (개발 운영 범위)** · 승인자: 사용자 · 기록일: 2026-09-18 · 제품 규칙 변경 없음

사용자는 ENG-02의 연속 개발 방향을 유지하되, 모든 하위 작업을 Astra로 실행하는 비용 비효율을 피하도록 역할별 모델 라우팅을 적용하라고 요청했다.

- 루트 Astra: 계획·분해·교차 모듈 통합·Hard Stop·최종 판정. 기본 코드 워커가 아니다.
- Sol high: 비사소한 구현, 상태 머신, 저장/네이티브 경계, 교차 모듈 수정.
- Terra medium/high: 각각 탐색과 읽기 전용 독립 리뷰.
- Luna low: 좁고 반복적인 고볼륨 수정과 fixture/test 확장.
- Codex-Spark: 사용 가능할 때 짧고 표적화된 즉답형 코딩 반복. 미지원 시 정상 폴백.
- 공유 AGENTS에는 제품 사실/완료 조건/권한만 두고 모델별 절차는 역할 TOML로 이동한다.
- 하위 역할이 실제로 Astra를 상속한 것이 확인되면 비용 보호를 위해 반복 사용하지 않고 `ROUTING_MISMATCH`로 기록한다. 실제 모델 확인이 불가능하면 `ROUTING_UNVERIFIED`다.

ENG-03은 ENG-02를 폐기하지 않고 **실행 비용/역할 배정 방식을 구체화해 대체**한다. 제품 DEC-01~32와 Hard Stop은 그대로다.
